# Consumer authentication operations

Supabase Auth is the consumer identity and session provider. The Web server verifies
cookies with `auth.getUser()` and cryptographically verified `auth.getClaims()` for every protected page and account route. Cookie
claims, browser-supplied user IDs and matching email addresses never determine the
Core subject. Anonymous Supabase users do not receive consumer access.

## Configuration

- `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`: public project
  configuration. Never supply a service-role key to the browser.
- Configure Google OAuth, email OTP delivery, redirect allowlists and session
  policy in Supabase. The Web callback is `/auth/callback`; register the exact
  production origin `https://app.voxagent.in` with the provider.
- `VOX_CONNECTED_APPS_REDIRECT_URI`: exact public connected-service callback,
  normally `https://app.voxagent.in/apps/oauth/callback` on the consumer subdomain.
  It is separate from Supabase's login `/auth/callback`. Add this same URI to Core's
  `VOX_MCP_OAUTH_REDIRECT_URIS`. For a shared-origin `/app` deployment use the actual
  `/app/apps/oauth/callback` path. Explicitly configure the production URI rather
  than deriving it from reverse-proxy request origins.
- Register Web as a Core host in `vox.standalone.deployment`. Store only these
  server variables: `VOX_CORE_URL`, `VOX_HOST_CREDENTIAL_ID`, `VOX_HOST_AUDIENCE`,
  `VOX_HOST_SECRET`. The expected host audience is
  `vox-host:vox.standalone.deployment:vox-web`.
- Every Core request signs `vox-account:supabase:<provider>:<verified identity UUID>` as the
  host user. Core resolves its own isolated user context; a Supabase UUID is not
  a Core context ID. No separate consumer account database, SMTP client, Ed25519 signing
  key or separate recovery-enrollment API is required.

The minimal consumer environment is the two public Supabase values, the four Core
host variables and the connected-service callback above. Web does not use or need
`SUPABASE_JWT_SECRET`: the Supabase SDK verifies tokens using the configured Auth
service/JWKS. The optional administrator console separately uses `SUPERUSER_EMAILS`,
`VOX_ADMIN_ORIGIN`, `VOX_CORE_ADMIN_URL` and `VOX_ADMIN_TOKEN`; these do not establish
consumer host trust. Store server secrets only in the deployment environment.

## Identity and session behavior

Google sign-in and email OTP remain available for standalone identities. Each
session must carry a signed `vox_identity` claim generated by the custom access-token hook below. Web requires a matching sole service-verified identity, session,
user, issuer and authentication method. Anonymous, unsupported, mixed and
multi-identity sessions receive no Core authority. Display metadata is never proof.

Supabase still automatically links same-email OAuth identities; this adapter does
**not** claim to disable that behavior. Automatically merged identities cannot
inherit Vox authority: the hook withholds the claim and Web rejects any current
multi-identity user. An immutable session pin prevents token refresh from binding
a replacement identity after unlinking. A fresh replacement login receives a
different Core subject. The existing manual linking action has been removed;
explicit dual-proof linking is a separate required follow-up, not feature complete.
See [Supabase identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking)
and [custom token hooks](https://supabase.com/docs/guides/auth/auth-hooks/custom-access-token-hook).

### Install the single Supabase identity adapter

1. Apply `supabase/migrations/20261001174921_consumer_session_identity_pins.sql`
   to the **configured Supabase Auth project**, using an authorized migration
   operator. This private provider schema is separate from Core identity storage.
2. In Supabase Authentication → Hooks, register the Postgres custom access-token
   hook `vox_auth.custom_access_token_hook`. For local Supabase configuration the
   URI is `pg-functions://postgres/vox_auth/custom_access_token_hook`. Keep the
   schema out of exposed Data API schemas; grant neither table nor function access
   to `anon` or `authenticated`. No service-role key belongs in Web.
3. Require a fresh sign-in after installing. Existing unpinned sessions fail closed;
   refresh cannot bootstrap a pin. This is a prelaunch subject reset: no continuity
   with the former merged-user UUID subject is retained.
4. Verify standalone Google and OTP logins; same-email auto-link denial; identity
   replacement denial for an old session; fresh replacement login isolation;
   refresh continuity; and signed Web → Core owned-agent access.

The migration supplies immutable insert/read-only pins to the trusted Auth role.
It does not mutate Supabase internal tables or link identities. Pins deliberately
survive identity deletion so refresh cannot rebind a replaced identity. Maintenance
may remove pins for deleted Auth sessions after their maximum access-token lifetime;
there is no browser-accessible pin creation, update, deletion or recovery fallback.
`getClaims()` checks JWT validity, and `getUser()` verifies the current user;
these do not promise instantaneous invalidation of already issued access tokens.
Supabase owns token lifetime, delivery limits and local/global sign-out.

### Explicit dual-proof linking follow-up

Use this same adapter and a durable identity-to-Vox-account binding, rather than a
second auth stack. The linking flow must authenticate the current pinned identity,
create a short-lived single-use intent bound to that session and target account,
then obtain a separate verified sign-in proof for the new identity. A trusted server
transaction must consume both proofs, reject conflicts/concurrent intent reuse,
record consent/audit events, and map the two immutable identities to the selected
Vox account. Email equality and Supabase's merged user UUID remain non-authoritative.
The token hook must select the proven session identity from immutable pins and
approved bindings, including when multiple identities exist; it must never choose
an identity from mutable display metadata. Unlink/recovery requires equivalent
proof and revokes affected bindings and sessions. Test collision, replay, expiry,
revocation and provider replacement before enabling the UI. Until that mechanism
exists, multi-identity users are denied access rather than automatically joined.

Consumer access does not grant administrator access. Administrator routes
independently require a verified superuser. Login identity linking grants no
external-service connection, assistant access or approval authority. Core enforces
these independently at its signed host boundary.

## Verification and release

Run `npm test`, `npm run lint`, `npm run build` and
`npm run test:e2e:consumer`. Also run `npm run test:auth-hook` with
`VOX_IDENTITY_TEST_DATABASE_URL` pointing only to a disposable empty PostgreSQL
database; the test uses real role grants/RLS and rolls back its Supabase-compatible
Auth schema fixtures. The consumer fixture uses the real Supabase client
against a local fake authentication service and a stateful Core fixture; it is
not evidence of production provider availability or Core host readiness.

Before releasing a new account-feature UI, verify an actual signed-in account
can retrieve its owned assistants, reviewed catalog and agent memory through
Web and the deployed Core. Verify revoked sessions, rejected host credentials,
Core downtime and foreign-origin mutation rejection. Live OAuth install,
consent, grants, read and revoke need separate provider evidence.

Removing the former Better Auth implementation does not delete an existing
`vox_web_auth` database schema or revoke its historical data automatically.
No live database mutation or credential rotation is part of this code change.

### Token issuance ordering review

The official [Auth token service](https://github.com/supabase/auth/blob/master/internal/tokens/service.go)
creates the session and its authentication claim before issuing the token, then
invokes the custom access-token hook with the same transaction. This supports
the hook's session-existence check at initial login; refresh cannot bootstrap a
new pin. Local SQL tests cover the policy, while live hook registration and
actual OAuth/OTP issuance remain release gates. The review also checked the
current [custom-token-hook contract](https://supabase.com/docs/guides/auth/auth-hooks/custom-access-token-hook)
and Auth changelog before release; the deployed Auth version still needs a live
compatibility check.
